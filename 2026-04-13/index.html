E-Mail Versand (SMTP) – Umsetzung

Ich habe den E-Mail Versand in meinem Gutscheinsystem umgesetzt.

Dafür habe ich zuerst lokal Docker verwendet und mit Mailpit einen SMTP-Testserver eingerichtet. Mailpit läuft dabei auf 127.0.0.1:1025 und die Weboberfläche ist über localhost:8025 erreichbar. So konnte ich Mails testen, ohne dass sie wirklich versendet werden. Anschließend habe ich die Mail-Einstellungen in der .env-Datei angepasst und Laravel so konfiguriert, dass es über SMTP mit Mailpit kommuniziert. Danach habe ich eine einfache Test-Mail über eine Route versendet und überprüft, ob sie in Mailpit ankommt.

Im nächsten Schritt habe ich eine eigene Mail-Klasse (VoucherMail) mit php artisan make:mail erstellt. Diese habe ich so angepasst, dass ein Gutschein (Voucher) übergeben wird. Dadurch kann ich in der Mail direkt auf die Daten des Gutscheins und des zugehörigen Schülers zugreifen. Zusätzlich habe ich eine eigene Blade-Datei (emails/voucher.blade.php) erstellt, in der die Inhalte der Mail definiert sind.

Zum Testen habe ich eine temporäre Route (/test-mail) verwendet, die einen Gutschein aus der Datenbank lädt und die Mail an die hinterlegte E-Mail-Adresse des Schülers sendet. Die Mail wurde erfolgreich in Mailpit angezeigt.

Automatischer Versand von Gutscheinen – Umsetzung

Nach dem grundlegenden E-Mail Versand habe ich den nächsten Schritt umgesetzt, nämlich den automatischen Versand von Gutscheinen.

Zuerst habe ich eine Funktion eingebaut, mit der Gutscheine geplant versendet werden können. Dabei wird beim Genehmigen eines Gutscheins optional ein Datum und eine Uhrzeit (scheduled_send_at) gespeichert.

Anfangs habe ich dafür einen eigenen Artisan Command erstellt, der regelmäßig prüft, ob geplante Gutscheine versendet werden müssen. Dieser Ansatz hat grundsätzlich funktioniert, war aber nicht optimal, da der Command manuell oder über einen Scheduler ausgeführt werden muss.

Deshalb habe ich den Versand anschließend auf Laravel Queues umgestellt. Dafür habe ich die Queue-Verbindung über die Datenbank aktiviert und die notwendige Tabelle erstellt. Danach habe ich einen eigenen Job (SendVoucherMailJob) erstellt.

Dieser Job übernimmt:

  • Laden des Gutscheins inkl. Schüler
  • Generieren der PDF-Datei des Gutscheins
  • Speichern der PDF im Storage und Setzen von pdf_path
  • Versenden der E-Mail inklusive PDF-Anhang
  • Aktualisieren des Status auf „sent“
  • Setzen von sent_at
  • Zurücksetzen von scheduled_send_at

Für die PDF-Erstellung habe ich das Paket barryvdh/laravel-dompdf verwendet. Ich habe eine eigene Blade-View (pdf/voucher.blade.php) erstellt, welche das Layout des Gutscheins definiert. Diese PDF wird automatisch beim Versand generiert, gespeichert und anschließend als Anhang zur E-Mail hinzugefügt.

Zusätzlich habe ich die Möglichkeit implementiert, die PDF direkt in der Detailansicht eines Gutscheins anzuzeigen oder herunterzuladen. Dafür habe ich eigene Routen sowie Controller-Methoden erstellt, welche die PDF dynamisch generieren und im Browser darstellen oder zum Download bereitstellen.

Im Controller habe ich den Versand angepasst:

  • Beim sofortigen Versand wird der Job direkt dispatcht
  • Beim geplanten Versand wird der Job mit delay() bis zum gewünschten Zeitpunkt eingeplant

Damit die Jobs automatisch verarbeitet werden, wird ein Queue-Worker (php artisan queue:work) verwendet, der im Hintergrund läuft.

Durch diese Umsetzung werden Gutscheine jetzt:

  • automatisch zum richtigen Zeitpunkt versendet
  • als PDF generiert und gespeichert
  • mit PDF-Anhang per E-Mail versendet
  • ohne manuelle Ausführung eines Commands verarbeitet
  • auch bei mehreren gleichzeitigen Versandvorgängen zuverlässig abgearbeitet

PDF für Gutscheine – Umsetzung

Zusätzlich habe ich die PDF-Funktion für Gutscheine umgesetzt und weiter verbessert.

Zuerst habe ich mit dem Paket barryvdh/laravel-dompdf die technische Grundlage geschaffen, um aus einer Blade-View automatisch eine PDF-Datei zu erzeugen. Dafür habe ich eine eigene View (pdf/voucher.blade.php) erstellt, welche das Layout des Gutscheins definiert.

Anschließend habe ich im VoucherController Methoden eingebaut, um die PDF direkt im Browser anzuzeigen oder herunterzuladen. Dabei wird die PDF dynamisch auf Basis der gespeicherten Gutscheindaten generiert.

Danach habe ich die PDF-Erstellung in den Versandprozess integriert. Beim Versenden eines Gutscheins wird die PDF automatisch erzeugt, im Storage gespeichert und der Dateipfad in pdf_path hinterlegt. Diese PDF wird anschließend automatisch als Anhang der E-Mail mitgesendet.

Im nächsten Schritt habe ich das Design der PDF schrittweise verbessert. Dabei habe ich mich am ursprünglichen Gutschein-Layout orientiert, das Design aber moderner und übersichtlicher umgesetzt. Es wurden unter anderem folgende Inhalte berücksichtigt:

  • Logos der Schule
  • Ort und Datum
  • Gutscheinüberschrift
  • Vorlage bzw. Anlass des Gutscheins
  • Name und Matrikelnummer des Schülers
  • Art und Anzahl des Gutscheins
  • Gültigkeitsdatum
  • Genehmigungs- und Ausstellungsdatum
  • Gutscheincode
  • Kontaktdaten der Schule im unteren Bereich

Zusätzlich habe ich die Darstellung der Unterschrift des Direktors und des Schulstempels vorbereitet bzw. eingebunden. Diese werden als Bilddateien verwendet, damit sie später bei Änderungen einfach ausgetauscht werden können.

Einlösung von einem Gutschein, aber mehreren Tagen (Teileinlösung)

Ich habe das Gutscheinsystem so erweitert, dass Gutscheine nun nicht mehr nur komplett, sondern auch teilweise eingelöst werden können. Das bedeutet, dass z. B. bei einem Gutschein über mehrere Tage nicht alles auf einmal verbraucht werden muss.

Dafür habe ich zusätzlich die ursprüngliche Anzahl des Gutscheins gespeichert, damit später nachvollziehbar bleibt, wie viele Einheiten ursprünglich vorhanden waren. Die aktuelle Anzahl wird weiterhin im Feld amount gespeichert und bei jeder Einlösung reduziert.

Außerdem habe ich eine eigene Struktur für den Einlösungsverlauf umgesetzt. Dabei wird jede einzelne Einlösung separat gespeichert. So kann ich im System genau sehen, wann ein Gutschein eingelöst wurde, wie viele Einheiten eingelöst wurden und welche Person die Einlösung durchgeführt hat.

In der Detailansicht habe ich das Ganze sichtbar gemacht. Dort werden jetzt die ursprüngliche Anzahl, die verbleibende Anzahl sowie alle bisherigen Einlösungen angezeigt. Zusätzlich habe ich ein Formular eingebaut, mit dem man eine bestimmte Anzahl direkt einlösen kann.

Die PDF habe ich bewusst nicht verändert, damit sie weiterhin übersichtlich bleibt. Sie zeigt nur den aktuellen Stand des Gutscheins.

Test mit Handy – QR-Code scannen

Ich habe den QR-Code zunächst lokal getestet. Dabei ist mir aufgefallen, dass ein Zugriff über das Handy nicht möglich ist, da die lokale Domain gutscheinsystem.test nur auf meinem eigenen Laptop funktioniert und von externen Geräten nicht erreichbar ist.

Um den QR-Code realistisch testen zu können, habe ich anschließend mit ngrok gearbeitet. Dadurch konnte ich eine öffentliche URL erzeugen, die direkt auf mein lokal laufendes Projekt verweist. Nach dem Start von ngrok mit dem Befehl ngrok http 80 habe ich eine temporäre Internetadresse erhalten, die ich für den QR-Code verwendet habe.

Mit dieser URL war es dann möglich, den QR-Code mit dem Handy zu scannen und auf die Einlöse-Seite zuzugreifen. Der gesamte Ablauf konnte erfolgreich getestet werden, vom Scannen bis hin zur tatsächlichen Einlösung eines Gutscheins.

QR-Code fertigstellen

Im nächsten Schritt habe ich den QR-Code vollständig in das System integriert. Dabei habe ich bewusst den Gutscheincode und nicht die ID verwendet, da dieser eindeutig ist und nicht einfach erraten werden kann.

Der QR-Code wird sowohl in der Detailansicht eines Gutscheins als auch im generierten PDF angezeigt. Im PDF habe ich ihn im oberen Bereich mittig platziert, sodass er gut sichtbar und einfach scanbar ist, ohne das Layout zu stören.

Beim Scannen des QR-Codes wird der Benutzer auf eine eigene Einlöse-Seite weitergeleitet. Dort werden die wichtigsten Informationen zum Gutschein angezeigt und es besteht die Möglichkeit, den Gutschein einzulösen. Die Einlösung erfolgt bewusst nicht automatisch beim Scannen, sondern erst nach einer Bestätigung durch den Benutzer.

Zusätzlich habe ich die Teil-Einlösung umgesetzt. Das bedeutet, dass ein Gutschein nicht nur vollständig, sondern auch in mehreren Schritten eingelöst werden kann. Jede einzelne Einlösung wird im System gespeichert, inklusive Datum, Uhrzeit, eingelöster Anzahl und Benutzer, der die Einlösung durchgeführt hat.

Außerdem habe ich sichergestellt, dass eine Einlösung nur unter bestimmten Bedingungen möglich ist. Der Gutschein muss den Status „versendet“ haben, darf nicht abgelaufen sein und es muss noch eine verfügbare Anzahl vorhanden sein.

Aus Sicherheitsgründen habe ich den Zugriff auf die Einlöse-Seite so geregelt, dass nur eingeloggte Benutzer darauf zugreifen können. Zusätzlich wird überprüft, ob der Benutzer die Berechtigung hat, Gutscheine einzulösen. Dadurch wird verhindert, dass unbefugte Personen Gutscheine einsehen oder verwenden können.

Archivierungs- und Löschkonzept der Gutscheine

Im Laufe der Entwicklung meines Gutscheinsystems habe ich mich mit der langfristigen Speicherung und datenschutzkonformen Verwaltung von Daten beschäftigt. Zu Beginn hatte ich mir gedacht, Schüler manuell zu deaktivieren oder zu löschen. Diese Idee habe ich jedoch überarbeitet, da dadurch Probleme bei bestehenden Beziehungen zu Gutscheinen entstehen könnten. Insbesondere hätte dies zu Datenverlust oder schlechten Verknüpfungen geführt. Aus diesem Grund habe ich mich für ein automatisiertes Archivierungs- und Löschkonzept entschieden.

Gutscheine bleiben zunächst bis zum Ablauf ihrer Gültigkeit im aktiven System sichtbar. Sobald das Ablaufdatum erreicht ist, werden sie automatisch archiviert. Technisch habe ich dafür das Feld archived_at in der Tabelle vouchers eingeführt. Aktive Gutscheine werden über whereNull('archived_at') geladen, während archivierte Gutscheine über whereNotNull('archived_at') in einer eigenen Archivansicht dargestellt werden. Dadurch bleibt eine klare Trennung zwischen aktuellen und archivierten Daten bestehen.

Die archivierten Gutscheine werden für einen Zeitraum von fünf Jahren gespeichert. Erst nach Ablauf dieser Frist erfolgt die endgültige Löschung. Diese Logik habe ich in einem eigenen Artisan-Command (app:process-voucher-archive) umgesetzt. Der Command archiviert zunächst abgelaufene Gutscheine und löscht anschließend alle Datensätze, deren Archivierungsdatum mehr als fünf Jahre zurückliegt. Dabei werden auch zugehörige PDF-Dateien entfernt, sofern diese vorhanden sind. Dies erfolgt über die Laravel-Storage-Funktion mit Storage::disk('public')->delete(...). Die endgültige Löschung des Gutscheins wird mit forceDelete() durchgeführt.

Parallel dazu habe ich die Verwaltung der Schülerdaten angepasst. Anstatt Schüler manuell zu löschen oder per Soft Delete zu deaktivieren, werden diese ebenfalls automatisch nach fünf Jahren entfernt. Dafür habe ich das Feld stored_at eingeführt, das den Zeitpunkt der Speicherung dokumentiert. Schüler werden jedoch nur dann gelöscht, wenn keine Gutscheine mehr mit ihnen verknüpft sind. Dies prüfe ich über eine Abfrage mit doesntHave('vouchers'), um Datenkonsistenz sicherzustellen.

Damit Gutscheine auch nach der Löschung eines Schülers weiterhin nachvollziehbar bleiben, speichere ich zusätzliche Snapshot-Daten direkt im Gutschein. Dazu gehören Vorname, Nachname und Matrikelnummer des Schülers. Diese werden beim Erstellen eines Gutscheins in eigenen Feldern gespeichert und bleiben unabhängig vom ursprünglichen Schülerdatensatz erhalten.

Zusätzlich habe ich die Datenbankbeziehung angepasst. Das Feld student_id in der Tabelle vouchers ist nun nullable und verwendet nullOnDelete(). Dadurch bleibt ein Gutschein bestehen, auch wenn der zugehörige Schüler gelöscht wird. Die direkte Beziehung wird in diesem Fall auf null gesetzt, während die Snapshot-Daten erhalten bleiben.

Die gesamte Archivierungs- und Löschlogik wird automatisiert durch den Laravel Scheduler ausgeführt. In der Datei routes/console.php habe ich den Command mit Schedule::command('app:process-voucher-archive')->daily(); eingebunden. Dadurch läuft der Prozess regelmäßig im Hintergrund, ohne dass ein manueller Eingriff notwendig ist.

Zur Überprüfung der Funktionalität habe ich Tests mit Laravel Tinker durchgeführt. Dabei habe ich gezielt Testdaten erstellt und Zeitstempel angepasst, um den Ablauf bei abgelaufenen und archivierten Gutscheinen zu simulieren. So konnte ich sicherstellen, dass die Archivierung, die endgültige Löschung sowie die Behandlung der Schülerdaten korrekt funktionieren.

Technische Umsetzung der Benutzerverwaltung

Die Benutzerverwaltung wurde im System vollständig über Laravel umgesetzt. Dabei habe ich auf das integrierte Authentifizierungssystem aufgebaut und dieses an die Anforderungen des Gutscheinsystems angepasst.

Zunächst wurde das bestehende User-Modell erweitert. In der Datenbank habe ich dafür zusätzliche Felder eingeführt, insbesondere role zur Unterscheidung der Benutzerrollen sowie can_issue_vouchers, um die Berechtigung zum Erstellen von Gutscheinen bei Lehrkräften zu steuern. Die Rollen werden als einfache String-Werte wie „teacher“, „secretariat“ oder „director“ gespeichert.

Im Model selbst habe ich verschiedene Methoden implementiert, um die Berechtigungen zentral zu steuern. Dazu gehören beispielsweise isTeacher(), isDirector() oder canCreateVouchers(). Diese Methoden werden im gesamten System verwendet, um Zugriffe auf Funktionen gezielt zu erlauben oder zu verhindern.

Die Erstellung neuer Benutzer erfolgt über einen eigenen UserController. In der store-Methode werden die Eingaben zunächst validiert, beispielsweise auf eindeutige E-Mail-Adressen und sichere Passwörter. Das Passwort wird anschließend mit der Laravel-Funktion Hash::make() verschlüsselt gespeichert. Beim Anlegen eines Sekretariatskontos wird die Berechtigung zum Erstellen von Gutscheinen automatisch gesetzt, während diese bei Lehrkräften optional aktiviert werden kann.

Die Zugriffskontrolle wurde sowohl im Backend als auch im Frontend umgesetzt. Im Controller werden kritische Bereiche, wie die Benutzerverwaltung, mit Abfragen wie auth()->user()->isDirector() geschützt. Zusätzlich werden in den Views bestimmte Menüpunkte und Funktionen nur angezeigt, wenn der Benutzer die entsprechenden Berechtigungen besitzt, beispielsweise durch Bedingungen wie @if(auth()->user()->canCreateVouchers()).

Für das Löschen von Benutzern habe ich Soft Deletes verwendet. Dadurch werden Benutzer nicht endgültig aus der Datenbank entfernt, sondern lediglich als gelöscht markiert. Dies wird durch das Feld deleted_at realisiert. So bleiben bestehende Verknüpfungen, etwa zu ausgestellten Gutscheinen, weiterhin erhalten und können nachvollzogen werden.

Fehlermeldungen und Meldungen im Allgemeinen

Ich habe das gesamte Meldungssystem im Projekt überarbeitet und einheitlich gemacht. Zuvor wurden Meldungen teilweise als einfache Browser-Popups oder als statische Boxen im Layout angezeigt. Diese wirkten nicht einheitlich und haben optisch nicht zum restlichen Design gepasst.

Deshalb habe ich ein eigenes System für Meldungen umgesetzt. Erfolgs-, Fehler- und Hinweismeldungen werden jetzt als kleine Toast-Nachrichten oben rechts angezeigt und verschwinden nach kurzer Zeit automatisch wieder. Dadurch bleibt die Oberfläche übersichtlich und wird nicht durch große Meldungsboxen unterbrochen.

Technisch habe ich dafür in der zentralen Layout-Datei (app.blade.php) eine eigene Toast-Funktion in JavaScript erstellt. Über diese Funktion können Meldungen mit verschiedenen Typen (z. B. success, error, warning) angezeigt werden. Die Meldungen aus Laravel (session('success'), session('error'), $errors) werden automatisch abgefangen und an diese Funktion übergeben, sodass sie direkt als Toast dargestellt werden.

Zusätzlich habe ich alle Bestätigungsabfragen, wie zum Beispiel beim Löschen oder Deaktivieren, durch ein eigenes Modal-Fenster ersetzt. Statt confirm() wird nun eine eigene Funktion verwendet, die ein gestaltetes Dialogfenster öffnet und erst nach Bestätigung die jeweilige Aktion ausführt.

API

Im Rahmen meines Projekts habe ich zusätzlich eine einfache API umgesetzt, um eine externe Schnittstelle für mein Gutscheinsystem bereitzustellen. Ziel dabei war es, ausgewählte Daten strukturiert im JSON-Format bereitzustellen und somit eine Grundlage für zukünftige Erweiterungen zu schaffen.

Die API wurde direkt innerhalb meines bestehenden Laravel-Projekts umgesetzt. Dabei habe ich eigene Routen definiert, die nicht für die normale Weboberfläche gedacht sind, sondern speziell für den Zugriff über Tools wie Postman.

Technisch basiert die API auf den Standardfunktionen von Laravel. Die Daten werden über Controller abgefragt und anschließend als JSON zurückgegeben. Dadurch können externe Systeme oder Entwickler die Daten einfach weiterverarbeiten.

Ein wichtiger Bestandteil der Umsetzung war die Trennung zwischen Web- und API-Routen. Während die normalen Seiten über klassische Web-Routen laufen, befindet sich die API in separaten Routen, wodurch eine klare Struktur entsteht. Zusätzlich habe ich darauf geachtet, nur die notwendigen Daten zurückzugeben, um die API übersichtlich und sicher zu halten. Die API wurde anschließend mit Postman getestet. Dabei konnte ich überprüfen, ob die Endpunkte korrekt funktionieren, ob die Daten richtig gefiltert werden und ob die Rückgabe im gewünschten JSON-Format erfolgt. Dieser Schritt war besonders wichtig, um sicherzustellen, dass die Schnittstelle stabil und fehlerfrei arbeitet.

Der konkrete Nutzen der API liegt aktuell vor allem in der Erweiterbarkeit des Systems. Auch wenn die API im jetzigen Stand hauptsächlich zu Testzwecken verwendet wird, bildet sie die Grundlage für zukünftige Funktionen. Dazu zählt beispielsweise die geplante Umsetzung einer abgesicherten REST-API mit Token-Authentifizierung (z. B. über Laravel Sanctum), über die berechtigte Benutzer wie Lehrkräfte Gutscheine genehmigen, versenden oder einlösen können.
